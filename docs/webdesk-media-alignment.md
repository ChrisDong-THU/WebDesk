# WebDesk 媒体链路改造与验证

目标场景为 Windows 主机 → 公网 → macOS 浏览器。设计依据是 [BilldDesk 实际安装包分析](billd-desk-installed-media-analysis.md)，不是将旧 Electron 源码当作当前客户端。实现独立编写，未复制或打包 BilldDesk 的 DLL。

## 实现

| 层次 | 本次改造 |
| --- | --- |
| 屏幕采集 | 可配置 Auto/DXGI/WGC/GDI；暴露实际后端、源帧新鲜度、采集/转换耗时、丢帧、错误和恢复原因。持续错误后有界重建及退避，GDI 稳定后试探恢复优选后端。 |
| CPU 路径 | 在全屏 BGRA→I420 之前缩放并按 sink FPS/像素预算过滤；跨分辨率变化仍保持四帧上限。安全桌面复用 libyuv SIMD 转换，保留原始 BGRA 管道。 |
| GPU 路径 | 独立 DXGI duplication → D3D11 VideoProcessor 缩放/BGRA→NV12 → 原生 texture buffer；四个不可提前覆盖的纹理槽，CPU I420 readback 后备。多屏合成、旋转等不支持条件继续已有 CPU 路径。 |
| NVIDIA 编码 | 可用设备优先直接 NVENC H.264：CBR、动态重配、低延迟、无 B 帧、请求 IDR。同 NVIDIA device 直接使用 NV12 texture；跨显卡直接读回/上传 NV12，避免 NV12→I420→NV12。统计明确区分 D3D11、CROSS-ADAPTER-NV12 与 CPU-NV12。 |
| 编码后备 | Windows Media Foundation 硬件 H.264，仅枚举硬件 MFT；低延迟、动态码率、无 B 帧，支持 D3D11 NV12 输入。纹理互操作失败可退 CPU NV12 硬编；硬编或动态码率控制失败使用同 H.264 软件后备。 |
| 协商 | 默认自动：根据能力、清晰/延迟目标及持续编码/解码压力有界选择 AV1/H264/VP9/VP8；可设置首选编码。浏览器尊重主机 Offer，保留全部 profile/repair 与兼容后备；实现回退与跨 codec 协商分开处理。见[后续编码复核](webdesk-auto-codecs-20261025.md)。 |
| 自适应 | 每两秒采样编码利用率、quality limitation、RTCP 丢包、RTT 和选中路径 BWE；区分 CPU/网络压力，有降级/恢复迟滞、冷却和用户画质上限。静态桌面低 FPS 本身不触发 CPU 降级。 |
| 恢复 | 信令存活时，同一个 peer 上做最多两次 ICE restart，保留音视频轨道和数据通道；协商 ID、ICE ufrag 世代过滤阻止旧 SDP/候选污染。信令断开时，回收旧 peer，网页在 60 秒内有界退避尝试重新授权、建立新会话；手动取消、页面关闭或认证失败终止。 |
| 浏览器 | 新增清晰/流畅/平衡/保持两者与低延迟设置，显示实际采集和编码诊断。采集 watchdog 只在源长期停止进展且 native 未自行恢复时重建。 |

低延迟模式使用更严格的应用层网络压力阈值。没有照搬 BilldDesk 未恢复出的全局 GoogCC/AIMD 参数，也没有关闭 WebRTC 拥塞控制。视频失败后改走截图传输不是本次方案：安装包证据没有证明这种自动降级存在。

持续丢包独立于 RTT 判定：自动模式的连续采样丢包超过 4%，低延迟模式超过 2%，即可进入原有三次迟滞和十秒冷却的有界降级。不能要求同时出现高 RTT：本机真实 2 Mbps 瓶颈在 RTT 60–150 ms 时已出现 5%–10% 丢包和整帧冻结。基于 BWE 的码率上限仍保留余量，持续健康后逐步释放；正常 1% 随机丢包或孤立突发不会因此反复降级。

动态码率设置必须返回 `S_OK`；`S_FALSE` 表示只读，不能因 `SUCCEEDED(S_FALSE)` 而继续使用不受拥塞控制约束的硬编。允许设置但读回未更新的驱动在两个输出后验证，不符合时转软件。当前设备确实复现了只读返回，这也是最初弱网实验回归后加入安全回退的原因。标准语义见 [Microsoft ICodecAPI::SetValue](https://learn.microsoft.com/en-us/windows/win32/api/icodecapi/nf-icodecapi-icodecapi-setvalue)。设置 `WEBDESK_DISABLE_HARDWARE_H264=1` 可在进程启动前显式禁用硬编，便于同 codec 对照及运维回退。

另一个已通过修复前后同测验证的问题是来源列表的 DXGI 所有权：原列表缓存会提前持有同进程 output，使独立纹理捕获器返回 `E_INVALIDARG`。Windows 枚举/缩略图改用 GDI，实际视频捕获仍独立选择后端。51 项采集回归覆盖先枚举再建立纹理采集、CPU 回退释放后的重新建立、staging 复用，以及 16ms/33ms 定时下不会把采集帧率误减半的累计限帧预算；新增运行中 GPU→CPU→GPU、保留帧、静态持续出帧、尺寸限制、重复切换和停止后拒绝调用。

采集路线也根据实际会话证据回退：连续三个有新编码帧的样本明确报告 `WebDesk-NVENC-H264-CROSS-ADAPTER-NV12`、纹理路径活跃，且编码阶段耗时超过 8 ms 与帧预算 35% 的较大值时，只尝试一次在同轨道内切到 CPU 早缩放。低于目标一半的静态低帧率、缺失数据和同设备 `D3D11` 路径不触发。该路径后缀证明存在 CPU NV12 桥，不能替代通用适配器 LUID 身份判断。切换按捕获线程顺序释放 duplication 后重建，避免新旧采集者同时占用 output；不重建 peer、音频或工具通道，也不降低用户请求的分辨率/FPS。

原生插件还修复了整数帧率解析：Dart 传入整数 `60` 时，旧的 `findDouble` 返回 0 并保留默认 30 FPS。新解析兼容整数/小数，使用与 sender 一致的 60 FPS 上限；旧调用可省略新增的高度限制。修复后的性能对照要显式使用实际 30 FPS 比较基线，60 FPS 另做有效性测试。

真实客户端测试还暴露了驱动初始化并发问题：独立 NVENC 单元测试通过，DLL 中与 Media Foundation 激活并发时却返回 `NV_ENC_ERR_INVALID_VERSION`，ABI 数字完全一致。修复后优先异步探测 NVENC，成功不启动 MF 探测；MF 后备延迟初始化，并串行化两套驱动的会话初始化。编码帧不持有初始化锁。两个初始化顺序、并发首次探测分别在独立进程验证，避免能力缓存掩盖竞态；通过公开 DLL 探测和真实 Chromium 接收链路再次确认 NVENC 实际生效。

## 构建与复核

`scripts/build-libwebrtc.ps1` 固定依赖版本，校验完整补丁栈，记录补丁/构建脚本和 DLL 哈希；插件使用与 DLL 同次构建的导出头文件。`scripts/prepare-flutter.ps1` 应用插件媒体桥接补丁。完整栈校验支持后层补丁改动前层上下文，并在不符合已知层次时保留本地修改、报错停止。

新增测试包括采集池/stride/颜色/早缩放/前置限帧、真实 GPU 合成颜色与纹理生命周期、硬件 H.264 I420/NV12/动态码率/暂停恢复、Dart 自适应与恢复时序、浏览器重协商和旧 ICE 世代过滤。

截至多编码自动策略与旧客户端兼容修正，94 项 Node 测试、92 项 Flutter 测试、Flutter 静态分析及正式构建通过。原生检查包括 51 项采集测试、9 项 NVENC 测试、3 个独立进程的首次初始化顺序复核、6 项 MF/禁用硬编测试，以及任务队列、标题栏输入和托盘回归；本轮原生 DLL/插件未改变。原生完整补丁栈校验和插件从固定原版重放、重复应用及逐文件哈希对照通过。正式构建入口为 `lib/main.dart`，测试入口未打入安装包。

真实媒体基准复用生产采集、编码选择、参数和自适应函数，通过 UDP 代理施加带宽、延迟和丢包。它使用独立测试程序与临时自有测试画面，不改动已安装客户端或服务。原始数据保存在 `test-results/billd-alignment/`，测试入口为 `desktop/flutter/test_driver/media_benchmark.dart`，不能作为生产入口发布。

## 当前边界

本机 Chromium 接收测试和合成设备测试不能证明 macOS Chrome 的公网性能，也不能代表与 BilldDesk 的同条件端到端对照。最终结论需要另一台 Mac 上的真实会话；比较时应记录浏览器/codec、分辨率/FPS、码率、实际编码器与硬件标记、P2P/TURN、RTT/丢包、采集/转换/编码耗时和输入到画面延迟。

网页自动重连兼容现有服务端，会重新建立会话；正在进行的文件传输和音频开启状态随旧会话回收。旧服务端有意合并“设备离线/密码错误”，收到该响应会停止自动重试，不能将其误报为已实现任意断网后的无缝恢复。

自动路径实测 `candidate-auto-path-30fps.json` 三组均保留 1728×1080，同轨道重建一次、最终 CPU 早缩放 + NVENC，实际后端 DXGI，采集错误为 0。为避免选择有利短测，追加 18 秒预热、30 次输入挑战的弱网长测：修复持续丢包规则前，新版 27.84 FPS、中位数 269.6 ms、P95 481.7 ms、四次冻结共 0.95 秒；旧版 23.26 FPS、中位数 290.7 ms、P95 395.2 ms、无冻结。该回归不能当作性能全面改善，促使本轮补上低 RTT 持续丢包的独立触发。原始数据为 `candidate-steady-weak-30fps.json` 与 `before-steady-weak-30fps.json`。

补上丢包规则后，完全相同的长测为 22.96 FPS、中位数 222.8 ms、P95 312.0 ms、一次冻结共 0.20 秒，平均编码阶段 7.50 ms，保留 1728×1080；相对旧版长测，延迟中位数下降约 23%、P95 下降约 21%，帧率基本相同。它通过主动降低帧率/码率预算换取较低排队和恢复成本，仍未消除所有冻结。原始数据为 `candidate-loss-budget-steady-30fps.json`；不能把它外推成 Mac 公网结果或 BilldDesk 性能差距。

Windows 最终候选为 `flutter-release/media-alignment-20261025/WebDesk-0.5.9-media-candidate-r2.exe`，SHA256 `36ceb30bfa4eb6d2be76de18533c5f92e8c3beacbc6024f0abd7b3c587e39058`，精确产物与部署记录为同目录的 `deployment.json`。候选仍用 0.5.9 版本号，不覆盖保留的旧安装包文件。安装需 Windows 管理员授权，用于更新应用与已有本机桌面服务。装好后打开客户端，确认服务地址并开启远控；Mac Chrome 强制刷新公网网页，使用 Windows 界面上的设备代码和密码连接。

首轮建议 1080p、30 FPS、8 Mbps 上限、自动降级，连续测试文字滚动、窗口拖动、动画约两分钟，记录状态栏编码器/FPS/RTT/P2P 或 TURN，以及卡顿和输入体感。随后在同会话改 60 FPS、流畅/清晰优先和低延迟模式，确认设置生效。最后短暂中断 Mac 网络再恢复，确认页面给出重连状态、新会话可用且没有残留按键；重新开启所需音频，重新发起中断的文件传输。
